1.1 THE PROBLEM
---------------
Small software teams need one place to see who is doing what. Typical student
projects stop at CRUD screens: create a task, refresh the page, hope for the
best. TeamPulse tries to go one step further:

  - A team workspace with roles (owner / admin / member / viewer).
  - Projects inside a team.
  - A Kanban board where cards can be dragged between five columns.
  - Live updates: when one person drags a card, other open browsers update
    without a refresh (WebSocket + Redis pub/sub).
  - Comments and an activity log on every task.
  - AI helpers: a daily standup summary and a task priority score, produced by
    a separate FastAPI microservice that calls Groq (Llama 3.3 70B).

The AI part is deliberately small. It is there to show that the author can
integrate an external API safely (timeouts, fallbacks, no key in the browser),
not to pretend the product is an AI startup.

1.2 WHAT A USER CAN ACTUALLY DO TODAY
-------------------------------------
Working end to end (verified by reading the code):
  - Register with email + password, or sign in with Google / GitHub.
  - Log in, stay logged in with a rotating refresh token, log out.
  - Create a team; the creator becomes owner.
  - Invite an existing registered user by email; change roles; remove members.
  - Create projects inside a team (name, key prefix such as WEB, description).
  - Open a project's Kanban board; create, edit, drag, assign and delete tasks.
  - Open a task detail page; edit fields; read comments; add, edit, delete own
    comments; read the activity log.
  - Ask the AI service to score a task's priority (button on the task page).
  - See the task priority badge (Low / Medium / High / Urgent).
  - Theme switching (light / dark / system), sidebar collapse.

Present but incomplete or mock (see Section 4 and remaining-tasks.txt):
  - Dashboard velocity and workload charts use hard-coded numbers.
  - "Today's Standup" button on the dashboard calls an endpoint that is broken
    (two separate bugs in backend/app/api/v1/ai.py).
  - Settings -> Notifications only writes to localStorage; nothing is saved on
    the server and no email is sent.
  - "Delete Account" and "Delete Team" buttons are not wired to the API.
  - AI project insights endpoint in the AI microservice returns an empty stub.
  - The assignee dropdown in the task modal is never filled because the board
    does not pass the member list (members defaults to []).
  - The AI priority result is displayed but not stored, so the task keeps its
    manual priority.
  - Live task/comment broadcasting is incomplete: sockets connect, presence and
    ping work, but no service ever calls manager.publish_event(), so a drag in
    one browser does not reach another browser yet. The client-side listeners
    are ready; the server-side emit is missing.

1.3 WHY THE PROJECT IS SPLIT INTO THREE SERVICES
------------------------------------------------
  frontend/    Next.js 14 - everything the browser sees. Also hosts NextAuth,
               which does the OAuth dance on the server.
  backend/     FastAPI - the only service that touches PostgreSQL and Redis.
               Owns authentication, permissions, business rules and WebSockets.
  ai-service/  FastAPI - a thin wrapper around Groq. Kept separate so that a
               slow or failing AI provider can never block login or the board.

The backend never calls the AI provider directly; it calls ai-service over HTTP
and falls back to a local heuristic if that call fails or times out.

2.3 WHAT THE SHAPE TELLS YOU
----------------------------
  - The repository is a monorepo: three deployable services side by side.
  - backend/app follows a layered layout: api -> services -> models, with
    core/ for infrastructure and schemas/ for request/response shapes.
  - frontend/src/app follows the Next.js App Router convention. Two route
    groups separate public auth pages from the private dashboard shell.
  - frontend/src/components is grouped by feature (kanban, tasks, teams, ai,
    charts) plus a ui/ folder of generic primitives.
  - docs/ is the documentation output folder. It was empty before this guide
    set was generated.
  - .github/workflows is empty: CI is planned but not implemented.

================================================================================
SECTION 5 - HOW EVERYTHING WORKS TOGETHER
================================================================================

5.1 THE THREE LAYERS
-------------------
  Browser
    Next.js pages (client components) hold UI state and form state.
    TanStack Query caches server data.
    NextAuth keeps a JWT session cookie (not the backend token).
    axios attaches credentials and/or a Bearer token.
        |
        | HTTP JSON over /api/v1, plus WebSocket
        v
  Backend (FastAPI)
    Router -> dependency (auth, rate limit) -> Service -> SQLAlchemy -> Postgres
    Service may also call Redis (rate limit, pub/sub) or the AI service.
    Response is validated by a Pydantic schema and returned as JSON.
        |
        v
  PostgreSQL (durable data) and Redis (ephemeral counters, pub/sub)
  AI service (optional): FastAPI -> Groq API -> text parsed into score/summary.

5.2 FLOW 1 - OPENING THE SITE
-----------------------------
  1. Browser requests https://<frontend>/ (or localhost:3000).
  2. Next.js serves app/page.tsx (a server component).
  3. The page is mostly static HTML + Tailwind; no API call is needed.
  4. "Get Started" and "Demo Login" are plain links to /login.

5.3 FLOW 2 - LOGIN WITH EMAIL AND PASSWORD (the most important flow)
-------------------------------------------------------------------
  1. User submits the form on /login.
  2. Frontend validates locally with zod (email shape, password non-empty).
  3. authApi.login() sends POST /api/v1/auth/login {email, password} with
     withCredentials: true.
  4. Backend auth route calls AuthService.login():
       - SELECT user by email.
       - bcrypt verify against password_hash.
       - Reject inactive users.
  5. create_token_pair(user.id, None, "member") builds:
       access token: 15 min, type=access, sub=user id
       refresh token: 7 days, type=refresh, sub=user id
  6. AuthService._store_refresh_token stores SHA-256(refresh) in refresh_tokens.
  7. The route sets two httpOnly cookies (access_token, refresh_token) on the
     response and returns both tokens in the JSON body.
  8. Browser stores the cookies automatically (this is why step 3 must happen
     in the browser, not inside NextAuth's server-side authorize()).
  9. The page then calls NextAuth signIn('credentials', ...).
 10. NextAuth's authorize() runs on the Next.js server and calls the backend
     /auth/login again (server-to-server, using BACKEND_INTERNAL_URL in Docker).
     It returns id/email/accessToken/refreshToken to NextAuth.
 11. NextAuth's jwt callback stores those tokens in its own encrypted JWT
     session cookie; the session callback exposes accessToken, refreshToken and
     user.id to the client.
 12. The page routes to /dashboard. From now on:
       - same-site local dev: the backend cookie authenticates requests;
       - cross-site production (Vercel -> Render): cookies are not shared, so
         the axios interceptor adds Authorization: Bearer <session accessToken>.
 13. When the access token is near expiry, api.ts calls POST /auth/refresh
     (cookie or body), and the backend rotates the refresh token. NextAuth's
     jwt callback also refreshes proactively using the stored refresh token.

5.4 FLOW 3 - LOADING THE DASHBOARD
----------------------------------
  1. app/(dashboard)/dashboard/page.tsx mounts (client component).
  2. useSession() reads the NextAuth session.
  3. useQuery(["teams"]) -> teamsApi.list() -> GET /api/v1/teams.
  4. Backend: get_current_user verifies the token; TeamService.get_user_teams
     joins team_members for this user and eager-loads members.
  5. JSON array returns; TanStack Query caches it for 60 seconds.
  6. A dependent query loops over each team's projects and calls
     GET /projects/{id}/tasks?assignee_id=<me>, merges results, sorts by due
     date and keeps five.
  7. Components render. The charts use hard-coded arrays (mock); the standup
     card waits for a button click.
  8. If any call returns 401, the axios response interceptor tries refresh once,
     then redirects to /login.

5.5 FLOW 4 - DRAGGING A KANBAN CARD
-----------------------------------
  1. KanbanCard is draggable (HTML5 drag data + dnd-kit sortable attributes).
  2. User drops it on KanbanColumn.
  3. Column computes position = tasks.length * 10 and calls
     onTaskMove(taskId, newStatus, position).
  4. KanbanBoard updates local state immediately (optimistic UI), then calls the
     page's move mutation.
  5. tasksApi.move -> PATCH /api/v1/projects/{projectId}/tasks/{taskId}/move
     body {status, position}.
  6. Backend: get_current_user -> TaskService.move_task:
       - loads the task, checks the caller is at least a member of the project's
         team;
       - if position is missing/None, appends after the current max;
       - updates status/position, writes an Activity row ("moved", old/new
         status and position), commits.
  7. Response is a TaskResponse; the page invalidates ["tasks", projectId] so
     the list re-syncs.
  8. Intended next step (not implemented): TaskService would call
     manager.publish_event(team_id, "task:moved", ...), Redis would fan it out,
     every backend worker's _listen_redis would broadcast to its sockets, and
     other browsers' KanbanBoard handlers would move the card. Today step 8
     does not happen because publish_event is never called.

5.6 FLOW 5 - COMMENTING ON A TASK
---------------------------------
  1. Task detail page loads GET /api/v1/tasks/{taskId} (direct router) and
     GET /api/v1/tasks/{taskId}/comments.
  2. New comment -> commentsApi.create -> POST /tasks/{id}/comments {content}.
  3. comments route resolves the task's team, requires membership, calls
     CommentService.create_comment: insert comment, log "commented" activity,
     commit.
  4. Response includes nested user; the page invalidates ["comments", taskId]
     and re-renders.
  5. Edit/delete are author-only (delete also allows owner/admin). The same
     "commented" activity action is reused for edit/delete, so the log does not
     distinguish them.

5.7 FLOW 6 - AI TASK PRIORITY
-----------------------------
  1. User clicks the AI priority button on /tasks/[taskId].
  2. Frontend -> POST /api/v1/ai/task-priority
     {task_title, task_description, due_date, assignee_workload: 0,
      project_velocity: 0}.
  3. Backend route requires login, creates AIService (httpx, 30s timeout) and
     POSTs to {AI_SERVICE_URL}/task-priority.
  4. AI service builds a prompt from prompts.py and calls Groq's
     /chat/completions with llama-3.3-70b-versatile, temperature 0.3.
  5. It parses SCORE, REASONING and ACTION, clamps the score to 1-10 and maps an
     invalid action to a score-based default.
  6. If Groq (or the service) fails, the AI service returns a heuristic score,
     and the backend has a second heuristic fallback as well.
  7. Frontend shows the result with PriorityIndicator. Nothing is written to the
     database, so ai_priority is always null on later loads.

5.8 FLOW 7 - WEBSOCKET CONNECTION AND PRESENCE
----------------------------------------------
  1. useWebSocket builds ws(s)://<NEXT_PUBLIC_WS_URL>/api/v1/ws/projects/<id>
     ?token=<accessToken>.
  2. Browser sends the HTTP Upgrade request.
  3. Backend websocket route reads the query token, verifies it, checks team
     membership, accepts the socket.
  4. ConnectionManager.connect adds the socket to the team room and broadcasts
     presence:update "online" to the room.
  5. Client may send {"event":"ping"} and receives pong, or presence:set with
     online/away/busy.
  6. On disconnect the manager removes the socket and broadcasts "offline".
  7. Cross-worker fan-out exists (publish_event -> Redis channel team:<id> ->
     psubscribe -> local broadcast), but only presence currently uses it.

5.9 WHERE AUTH AND PERMISSIONS ARE ENFORCED
-------------------------------------------
  Authentication (who are you):
    - jwt token signature + type check (core/security.py)
    - token from cookie or Bearer header (dependencies/auth.py)
    - user must exist and is_active
  Authorization (what may you do):
    - team membership is checked in TeamService/ProjectService/TaskService/
      CommentService.
    - role hierarchy viewer < member < admin < owner for task creation and
      management.
    - only owner/admin can change roles or remove members; only the owner can
      delete a team; the owner cannot be removed or demoted.
  Transport rules:
    - httpOnly cookies, SameSite=Lax, Secure in production.
    - refresh tokens stored hashed and rotated.
    - login/register/refresh/forgot/reset rate-limited per IP.
    - CORS restricted to configured origins with credentials allowed.
  Known soft spots:
    - WebSocket token travels in the query string (logged by some proxies).
    - forgot/reset password endpoints do not send email or validate a reset
      token properly (they are placeholders).
    - the frontend has no route guard mounted; protection is API-driven.

5.10 HOW THE DATA MODEL FITS TOGETHER
-------------------------------------
  User 1---* Team (owner)
  User *---* Team through TeamMember (role)
  Team 1---* Project 1---* Task
  Task *---1 User (assignee, optional)
  Task *---1 User (reporter, optional)
  Task 1---* Comment *---1 User
  Task 1---* Activity *---1 User
  User 1---* RefreshToken
  User 1---* OAuthAccount (provider identity)

  Delete behaviour:
    - deleting a team cascades to members and projects;
    - deleting a project cascades to tasks;
    - deleting a task cascades to comments and activities;
    - deleting a user sets task assignee/reporter to NULL but cascades their
      comments, activities and memberships.

---------------------------------------

  README.md -> frontend/src/app/page.tsx -> app/layout.tsx -> providers.tsx
  -> app/(auth)/login/page.tsx.

  -> core/security.py -> dependencies/auth.py.

  -> schemas/auth.py.
Day 4 - the board:

6.2 PLATFORM CHOICE AND WHY
---------------------------
  Frontend -> Vercel
    Why: Next.js is made by Vercel; the free Hobby plan builds from GitHub with
    no card, serves static assets from a CDN and runs serverless functions for
    NextAuth. A FastAPI process cannot run there.
  Backend -> Render (Docker)
    Why: The free plan runs a Dockerfile.prod container without a card. Render
    injects $PORT (handled by the Dockerfile), supports a health check path and
    auto-deploys on push. Trade-off: it sleeps after 15 minutes idle and takes
    about a minute to wake.
  Database -> Neon
    Why: Serverless Postgres 16, 1 GB free with no expiry, TLS by default. The
    code already rewrites sslmode=require for asyncpg. Use the direct host (no
    "-pooler") because the app uses a normal async pool.
  Redis -> Upstash
    Why: 250 MB free, TLS (rediss://), and the app only needs pub/sub plus a
    rate-limit counter. Render Key Value is an alternative when available.
  AI service -> not deployed
    Why: It is optional. With AI_SERVICE_URL unset, backend calls fail fast and
    AIService returns the heuristic score/summary. This keeps the free budget
    for the API. If you deploy it later, use Dockerfile.prod and set
    AI_SERVICE_URL to its public URL.
  Keep-alive -> cron-job.org
    Why: Pings /health every 10 minutes so the free Render service does not
    sleep. Render's 750 instance-hours/month is almost consumed by one always-on
    service (about 730 hours), so do not keep a second service awake.

6.6 HOW TO REDEPLOY
-------------------
  Code change (frontend or backend):
    1. git add . ; git commit -m "..." ; git push origin master
    2. Vercel auto-builds the frontend from the push.
    3. Render auto-builds the backend Docker image from the push.
    4. Watch both dashboards; the Render free build has no cache, so expect
       3-5 minutes.
  Environment variable change:
    - Render: edit the variable, then Manual Deploy -> Deploy latest commit
      (a plain restart is not always enough because the container is rebuilt).
    - Vercel: edit, then Deployments -> Redeploy, because NEXT_PUBLIC_* values
      are compiled into the bundle.
  Database schema change:
    1. Create a migration locally: alembic revision --autogenerate -m "msg".
    2. Review the generated file.
    3. Run alembic upgrade head against Neon (from a machine that can reach it),
       or rely on init_db()/create_all for additive changes.
    4. Never edit 001_initial.py after it has been applied somewhere.
  Seeding again:
    Run the same docker compose run command; seed.py skips rows that exist.

6.7 COMMON DEPLOYMENT PROBLEMS
------------------------------
  CORS error in the browser
    CORS_ORIGINS must be a JSON array with the exact origin (scheme + host, no
    trailing slash), and the frontend must be redeployed after changing
    NEXT_PUBLIC_API_URL.
  Render says "No open ports detected"
    Root directory must be backend and Dockerfile path ./Dockerfile.prod. The
    production CMD already binds to $PORT.
  Render crashes on boot with ConnectionError
    Bad REDIS_URL. Upstash needs rediss:// including the password; the lifespan
    hook initialises Redis before serving.
  500 on /auth/login
    Missing SECRET_KEY, or the database is unreachable/migrations not applied.
  "UntrustedHost"
    trustHost: true is missing in frontend/src/lib/auth.ts (it is present now).
  "Invalid connection option sslmode"
    Someone removed the sslmode -> ssl rewrite in core/database.py.
  WebSocket fails only in production
    NEXT_PUBLIC_WS_URL must be wss:// and must be set before the build.
  OAuth returns to /login?error=...
    Callback URL does not exactly match the deployed domain.
  Board empty after deploy
    Seed step skipped, or seeded against a different DATABASE_URL.
  Everything 502 for a minute
    Render cold start. The cron ping prevents it.
  Login works but API calls fail on Vercel
    Cookies are not shared between vercel.app and onrender.com. The Bearer
    fallback must be working; check that NextAuth exposes accessToken in the
    session.
  AI always returns generic scores
    AI_SERVICE_URL is unset or the AI service is asleep/not deployed. This is
    the designed fallback, not a crash.

7.1 GLOSSARY
------------
API            Application Programming Interface - here, the JSON endpoints
               under /api/v1 that the frontend calls.
Async          Code that can wait for I/O (database, network) without blocking
               the whole server. FastAPI and SQLAlchemy here are async.
Alembic        Database migration tool for SQLAlchemy. A migration is a Python
               file that upgrades/downgrades the schema.
Bearer token   An HTTP Authorization header: "Bearer <jwt>". Used when cookies
               cannot be shared across sites.
bcrypt         Slow password hashing algorithm. Passwords are never stored in
               plain text.
CORS           Cross-Origin Resource Sharing. The backend must explicitly allow
               the frontend's origin when they are on different domains.
CSP            Content-Security-Policy. A browser rule list that says which
               scripts/connections are allowed. A wrong connect-src blocks the
               API.
Docker         Packages an app and its dependencies into an image; a container
               is a running image.
Docker Compose Runs several containers from one YAML file.
dnd-kit        React drag-and-drop library used for Kanban sorting.
FastAPI        Python web framework with automatic validation and OpenAPI docs.
Groq           AI inference provider; this project calls its OpenAI-compatible
               chat completions API with Llama 3.3 70B.
httpOnly       A cookie flag that hides the cookie from JavaScript, reducing
               XSS token theft.
JWT            JSON Web Token: header.payload.signature. The payload here holds
               sub (user id), team_id, role, type, exp and iat.
Middleware     Code that runs around every request (logging, headers).
Migration      A versioned schema change (see Alembic).
Next.js        React framework with file-based routing and server components.
NextAuth       Authentication library for Next.js. It manages its own session
               cookie and supports Credentials/Google/GitHub providers.
ORM            Object-Relational Mapper: Python classes map to SQL tables
               (SQLAlchemy here).
PostgreSQL     Relational database. Data lives in tables with foreign keys.
Pydantic       Python validation library. Schemas check request bodies and
               shape responses.
Redis          In-memory store. Used for rate-limit counters and pub/sub
               messages between WebSocket workers.
Refresh token  Long-lived token used to get a new short-lived access token.
               Stored hashed in the database and rotated on use.
Render         Hosting platform used for the Dockerised API.
REST           HTTP style using methods (GET/POST/PATCH/DELETE) and resource
               URLs.
Route group    Next.js folder in parentheses, e.g. (dashboard); it groups files
               without adding a URL segment.
Schema         Either a database table definition or a Pydantic model,
               depending on context.
SQLAlchemy     Python ORM and SQL toolkit; version 2.0 style is used here.
SSE/WebSocket  Ways to push data from server to browser. This project uses
               WebSocket (full duplex).
TanStack Query Client-side cache for server data; handles loading, retries and
               invalidation.
tsbuildinfo    TypeScript incremental build cache file.
Upstash        Managed Redis provider with a TLS URL (rediss://).
Vercel         Hosting platform for the Next.js frontend.
Vitest         Unit test runner for the frontend.
Playwright     Browser automation used for end-to-end tests.
Zod            TypeScript schema validation, used with react-hook-form.
Zustand        Small React state store (sidebar, theme, toasts).
Uvicorn        ASGI server that runs the FastAPI app.

7.3 RUN LOCALLY WITHOUT DOCKER (WINDOWS POWERSHELL)
---------------------------------------------------
Prerequisites: Python 3.11+, Node 20+, PostgreSQL 16 and Redis 7 installed
locally (or run only those two with Docker).

  A. Start infrastructure only:
       docker compose up -d postgres redis

  B. Backend:
       cd backend
       python -m venv .venv
       .\.venv\Scripts\Activate.ps1
       pip install -r requirements-dev.txt
       Copy-Item .env.example .env
       # edit .env: DATABASE_URL, REDIS_URL, SECRET_KEY, AI_SERVICE_URL
       alembic upgrade head
       python scripts/seed.py
       uvicorn app.main:app --reload --port 8000

  C. AI service (optional):
       cd ai-service
       python -m venv .venv
       .\.venv\Scripts\Activate.ps1
       pip install -r requirements.txt
       Copy-Item .env.example .env
       # set GROQ_API_KEY
       uvicorn main:app --reload --port 8001

  D. Frontend:
       cd frontend
       npm install
       # create .env.local with:
       #   NEXT_PUBLIC_API_URL=http://localhost:8000
       #   NEXT_PUBLIC_WS_URL=ws://localhost:8000
       #   BACKEND_INTERNAL_URL=http://localhost:8000
       #   NEXTAUTH_URL=http://localhost:3000
       #   NEXTAUTH_SECRET=<random>
       #   GOOGLE_/GITHUB_ values if needed
       npm run dev

  E. Open http://localhost:3000.

  Common Windows issues:
    - PowerShell blocks venv activation: run
      Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass
    - psycopg/asyncpg build errors: use Python 3.11 or 3.12, not 3.13.
    - Port already in use: `netstat -ano | findstr :3000` then stop that PID.
    - NextAuth calls localhost from inside a container: set
      BACKEND_INTERNAL_URL=http://backend:8000.
